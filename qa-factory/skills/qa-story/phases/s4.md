## Case design, pinning and Gate A

Both roles go through the same three commands (`references/judge.md`), the designer first. The critic's verdict (`header.verdict` of its form) is recorded with `stage_done.py --acceptance` before its finish, and a critic that sends cases back on the last round goes to the conductor, not to a silent close:

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" start --task <TICKET> --stage S4 --role qa-case-designer
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" bind  --task <TICKET> --dispatch-id S4-qa-case-designer-1 --agent-id <id>
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" finish --task <TICKET> --dispatch-id S4-qa-case-designer-1 --digest "<digest>"
```

then the same three with `--role qa-case-critic` and `--scope <the case ids of the design-review rows>`. The
designer's `finish` leaves the stage open, the critic's closes it (`--not-complete` when its
verdict sends cases back). Pin the cases before the critic's `start`: with a judge configured it runs
`judge_cases.py` over every pinned case — none skipped — and the critic starts from
`work/judge-cases.json`. With `pipeline.stop_after: "gate_A"` the story ends after Gate A's
decision is recorded (the gate-decision answer's `next_action` is then `stop`): run what the
decision authorized, give the stand's config back (`python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" config-restore --task <TICKET>`; tell the person its `line` if it has one), say so in one line and stop.

Resolve the canonical case store and dispatch `qa-case-designer`. After cases and oracles
are ready, dispatch an independent `qa-case-critic` only for rows whose validated
`design_review_required` is true — the cases of those rows are the critic's scope (each case
file names its row in `Plan row:`; the `--scope` is case ids, never row ids), and naming them
in the dispatch is your step on this path: a critic left to choose its own scope reviews
whatever it happens to read. Simple unambiguous scope needs no extra critic call.
A case on a field whose value goes to the server or redraws the page is a case about behavior (value kept whole, focus kept), not about one `fill`.
Structural validation and traceability remain mandatory for every case. Allow at most two
repair/review rounds per affected case. Reuse or update existing text cases
before creating new ones. Prepare TMS create/update/reuse proposals, but do not publish
them before Gate A authorizes that external action.
Say in the dispatch text of the designer and of the critic: `work/test-plan.json` is read by section — a whole `Read`
of it is answered with the map of its rows (id: lines); read the rows you need with `offset`/`limit`.

**Pinning is your step, not the designer's.** The designer hands over case files and has no
Bash; `case_versions.py` is deterministic bookkeeping. When the designer returns, and again
after every repair round, run one batch for the whole story:
`case_versions.py --task-root <TASK_ROOT> --all` (it records the pinned cases as the approved
scope in the same step, and its answer's `review_scope` is the critic's `--scope`: the pinned
cases of the design-review rows, or every pinned case when the plan names none - take it, do not
count the cases of a row by hand). Then, as the precondition for dispatching
the critic — which reviews pinned versions and nothing else — run
`case_versions.py --task-root <TASK_ROOT> --verify`; it names any case whose current bytes are
unpinned. `--store` is not yours to invent: it defaults to the project's `config.cases_root`
when there is one and to `<TASK_ROOT>/work/test-cases` when there is not, which is also where
both commands look for the cases — on a project with its own case store, searching only the
story folder pinned nothing and Gate A approved an empty set. Neither command repairs a role's
artifact: it writes the orchestrator's own `state/story-case-links.json`. The same rule holds
on a resume: `stages.json` names S4's output `work/test-cases/`, but on a `cases_root` project
the cases are in the project's store — `case_versions.py --task-root <TASK_ROOT> --verify`
answering with a case count is the proof S4 produced them, and an empty story folder is not a
reason to design them a second time. An exit 1 with a reason names why no case was found; it is never a pass.

**An open blocking question stops the stage before the critic.** A question marked `severity:
blocker` (or marked nothing) that is still open stops S4 after the case designer's handoff and
before the critic starts: the person answers it first, or passes it with `go on`; the critic's
own return has no such stop. A question the person keeps open until the report is not asked
again; the cases keep its unanswered branch.

**A stray case file is yours to delete.** A handoff refused as `case identity: ...` is fixed by the
designer writing each case again under the name the refusal shows, but the file under the OLD name
stays in the tree and is refused again, and the designer has no tool to delete it. Once the new
file exists, you (the orchestrator, or the driver's conductor) delete each old file the refusal
named and nothing else, then pin as above. No new file, no deletion: never remove the only copy.
A person's word or `config.case_id_form` instead removes nothing.

**The critic's verdict is computed, not quoted.** `critic_rollcall.py` reads the roll-call in
`critic-findings.md`: an unreviewed row makes the verdict `partial`, the digest must read
"N of M reviewed", and the unreviewed case ids reach the Gate A message by name. The last
round's concerns that come with an exact replacement (verdict `approve_with_fixes`) are
applied by code, with no dispatch and no new round: `critic_rollcall.py --apply-fixes
--task-root <TASK_ROOT>` replaces the text, re-pins the case and checks it landed. A
replacement that matches zero or several places is left alone and is a Gate A debt with an
owner — the gate rehearsal then shows it as the person's call, never as a repair you owe, so
S4 closes over it instead of looping. A role with no Bash is never told to run a validator:
you run it, or the exit gate does.

**Two rounds, then the gate — not a halt.** The critic's second failing review of the same
case comes back as `done` with `verdict=reject`, not `halt`: the cap exists so the PERSON
decides at Gate A, and a halt would stop the pipeline in front of the gate that resolves it.
Carry the verdict and the case ids into the Gate A message as they stand. What the person
hears between rounds is one sentence from code, never your own narration:
`stage_status.py --task <TICKET> --event critic_returned|author_repair` (`--event
state_repaired` after a recover).

Before Gate A run `render_case_appendix.py --task-root <TASK_ROOT> --output <TASK_ROOT>/work/case-appendix.md --plan <TASK_ROOT>/test-plan.md`. It embeds the exact pinned case steps and expectations into the plan; never compose them from memory or enumerate unrelated cases from the shared store.
