# S2 — Understanding and size

Use `references/coverage-design.md`. Every requirement retains a source revision, while the
oracle comes from confirmed requirements rather than implementation or a test name: code and another side's test
(`current-code:`, `derived_from: test:<ref>`) are never a `source`, and such a row waits for one question once its `source` is read (person-owned: requirement_intent). Keep
confirmed requirements, technical invariants, and derived risks distinct; ambiguity stays an owner
question and a derived access/data-loss risk may still be critical. The S2 brief's `User-path failures` lines (code by
`scripts/user_path_failures.py`) name places of the diff, or - with no diff - of the files S1 recorded in `context-bundle.json` (and files its notes name), that swallow a failure; the tester judges which lie on a user's path.

## Digest `halt` — `verdict: blocked`

```
qa-requirements-tester S2 halt · <path to understanding.md> · blocked — <N> blocking
question(s), understanding brief sent alone
```

This is the one case in the whole pipeline with three human touchpoints instead of two. Do
**not** run S3. Send the understanding brief by itself:

1. First line: the paths — `understanding.md`, `requirements-register.md`,
   `requirements-readiness.json`.
2. The understanding brief, at most 40 lines, as written.
3. The blocking questions from `requirements-readiness.json`'s `open_questions[]`, each as
   the role wrote it: the statement with its `owner_role` (`po_ba | dev_arch | qa`) and
   severity, what the sources say with where, and the readings lettered a/b/… with what each
   one costs. Never a one-line summary — a question the person cannot answer without opening
   a file is a question nobody answers (TP1-15045). A question that arrives without its
   readings goes back to `qa-requirements-tester`, never to the person.
4. One sentence: "There is no plan yet — it is built after these answers."

No plan items, no disposition items, no approval item. There is nothing to approve.

The driver records the answers: every whole-line token (`Q1: b`, `Q1: not needed`,
`Q1: until the report`) goes to the answers file by code, and the role resumes in its own
session with the person's words. Words that are not a token reach you whole: record each
answer with `question_register.py --task <TICKET> --answer|--not-needed|--defer <id>
--words-file <the file holding the words> --where "S2 stop" --by conductor --register-hash
<row_hash>` (`--show` prints the hashes); never write the answers file or the role's prompt by
hand. A second `blocked` verdict is the halt question again, with its options (answer in words,
or `stop`) — the requirements are not testable yet; each round the person answers costs one more
session of the role, and none runs without the person's answer (person-owned: requirement_intent).

## Exit

After the author's stop the driver dispatches `qa-case-critic` for this stage; its verdict is recorded with `stage_done.py --acceptance` before its finish; repair rounds follow `repair_budget`.

On `done`:

1. The size is computed, not quoted, and it is computed by the **role**: step 5 of its
   charter runs `sizing.py --task <TICKET>`, which writes `work/sizing.json` (weight per
   requirement by its `impact` class, reducers, diff signals, the arithmetic in
   `reasoning[]`; the size itself is `2 ×` the functions the register's `## Functions` table
   names, `size_unit` says which unit it is) before `understanding.md` quotes its Size line. The S2 exit detector runs
   the same script again and only re-verifies: a re-run preserves the `size_override` already
   on disk. Record `size` with `stage_done.py --task <TICKET> --set size=<XS|S|M|L|XL|XXL>`
   — never by editing `pipeline.json`, and it refuses anything outside that list; `XXL` is a
   gate A recommendation the person's word passes, never a block. A `size_override` the role
   recorded stays visible at gate A beside the computed one. A requirement whose `impact` is
   blank weighs 1.0 and the file says so.
2. **Accept the dispatch in the controller first** — the door is `story_step.py finish --task
   <TICKET> --dispatch-id <id> --digest "..."` (the one a refused hand-written accept prints): it
   writes the request whole. Only where it cannot run, by hand: `controller.py --task-root <TASK_ROOT>
   --operation accept --input <receipt>.json` (`references/controller-api.md` §3). A managed
   stage the controller has not accepted is refused by `stage_done.py`. Then record the
   stage: `stage_done.py --task <TICKET> --stage S2 --status done --role
   qa-requirements-tester --digest "<digest>"` — state and journal in one call.
3. Print the S3 card: `story_step.py card --stage S3`.

The S2 exit detector `branch_accounting.py` refuses a register in which a sentence of the story's text (or of a kept linked ticket) has no home in `## Source obligations`, or a branch has no row in `## Branches` (`--units`/`--unhomed --task <TICKET>` list the units, the person's word passes a refusal); an old register with no such section reads as legacy and is not refused. It also refuses a file (of the story or of a kept linked ticket) that has no row in `## Attachments` (`--attachments --task <TICKET>` lists them, each with the call that opens it); a story with no file owes no section, and a file is judged by the role, never by this script.

Do not read `requirements-register.md`. The human sees it at gate A; you never need its
contents to dispatch the strategist, only its path.
