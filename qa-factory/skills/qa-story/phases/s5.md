# S5 — Automation and independent review

Gate A approval for the current scope/revision is required. Follow
`references/execution-lifecycle.md`.

## The stand, before the first dispatch

Read `pipeline.json`. `environment` named and `environment_pending` false: a stand was
confirmed — go on, no second probe. Otherwise, unless `stage_overrides[]` already holds a
person's word on the block `stand not confirmed` (recorded on S5 or S6, it covers both):
with a name, run `env_probe.py --env <name> --task <TICKET>`; exit 0 →
`stage_done.py --task <TICKET> --set environment_pending=false`, go on. No name, or the probe
did not exit 0 → read the probe's three lines and cause first (`login: not_recorded` is the factory's, S0 says so; run an authorized `bring_up` first), then ask the person once, naming the stand if there is one: the name of a
configured stand, `retry` (after they bring it up, or record one with
`/qa-factory:qa-onboarding`), or `go on` to go without a stand. A stand name →
`stage_done.py --task <TICKET> --set environment=<id> --set environment_pending=true`, then
probe it as above; `go on` → `waiver.py --task <TICKET> --stage S5 --block "stand not
confirmed" --decision "<their words>"`. Dispatch nothing until one of these holds. (person-owned: access).

## The plan, before any window

On the earlier form, a story whose S5 began before this release, or was begun by the driver,
finishes S5 with windows only: `start --purpose s5_plan` is refused there and says so; go on with
the windows below. Every other story is planned first: stand → plan (automator, `--purpose s5_plan`) → plan
review (critic, `--purpose s5_plan`) → blocker? narrow plan rework, one re-look → windows. The
controller refuses a window before the plan has its review.

Both plan dispatches take every id of `--operation stage-scope`, never a window's, and run no test:

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" start --task <TICKET> --stage S5 --role qa-automator --purpose s5_plan --scope <every id>
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" finish --task <TICKET> --dispatch-id S5-qa-automator-<n> --digest - --not-complete
```

then the same two with `--role qa-code-critic`. `start` writes the skeleton `work/s5-plan.json`
(`s5_plan.py --init`); the author fills it and the dispatch ends at `s5_precheck.py`, which names
every gap of the plan at once. The critic's form (`outcome`, `remarks[]`) decides:

- `approved` / `approved_with_remarks`: the plan is not rewritten; each window gets its slice of
  the plan and the remarks of its cases.
- `blocked`: a blocker is what the window's author cannot repair inside the window (a Then with no
  test, an oracle not taken from the requirements, a level the stand cannot observe, a test with
  no target to extend); the rest is a `remark`. Rework the author on the blocker rows only
  (`controller.py --operation rework --stage S5 --role qa-automator --purpose s5_plan --brief`, the card
  goes to the same agent), then ONE more look of the same critic (`rework --role qa-code-critic
  --purpose s5_plan`), the blocker rows only. Blocked again: no window starts. A row the author can repair inside a window is a remark, not a question (person-owned: risk); put the choice to
  the person, each way with its cost (`references/human-questions.md`): `plan before windows` (the
  blocker travels into its window as a remark), `plan review round` (one more look), or their
  own decision; `waiver.py --task <TICKET> --stage S5 --block "<that word>" --words-file <file>`.
- Cases added to S5 after the review: the controller refuses their windows until the plan is
  reworked for them (`--purpose s5_plan --cases <new>`) and the critic has looked at the rows that
  moved; the refusal names the exact `--cases`.

After the plan review the windows follow the plan: the cases one test covers are one window, at
most 2 e2e-ui cases or 4 others, non-UI first, and a group larger than that is still one window
(`over_cap`). A window is its author's chain and is never cut again; a case added later whose test
reaches it grows it (`grown`): its author reworks it with the new case, then its critic, before S5
can close. A scope that splits a test is refused, and so is a fresh author over a written window.
`stage-scope` carries `window_cut`: for each window number in `grown`, run `controller.py
--operation rework --stage S5 --role qa-automator --cases <that window's scope> --cause
ticket_changed --reason "case(s) <new> added after the plan review" --brief` (no cap spent), then rework its
critic, a fresh one if none ran. When `window_cut.why` says the plan cut failed, the windows are cut
by cases and the plan gates refuse them: repair what `why` names first.

## Boundary and judge

A window is two roles, with the window's own scope typed nowhere but here — it comes from
`--operation stage-scope`:

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" start --task <TICKET> --stage S5 --role qa-automator --scope <the window's ids>
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" bind  --task <TICKET> --dispatch-id S5-qa-automator-<n> --agent-id <id>
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" finish --task <TICKET> --dispatch-id S5-qa-automator-<n> --digest - --not-complete
```

then the same with `--role qa-code-critic` and that window's scope; `--not-complete` on the last
one too while another window is still to come. `bind` is for a FRESH agent (window 1 is always fresh): on
Claude the plugin's hook runs it the moment the `Agent` call returns an id, so run it by hand only when the guard or `where` says the
dispatch is unbound (Codex, a prompt that is not the card's, a hook that failed); without a binding the resume guard refuses the
follow-up and `dispatch_liveness.py` can prove nothing. A resumed role needs none, its rework card carries the id. `finish --digest -` takes the digest `exit_gate` recorded in `work/digests/`; with no such file
it refuses and asks for the role's digest line, which `--digest "<digest>"` then gives. Back to a
role: `controller.py --operation rework`, then the card to the same agent with `SendMessage` (S5
resumes: `rework_mode`), never `pause`, which is only for a dispatch waiting on a person. A critic that
cannot judge because its AUTHOR's code is defective, while it still runs: `finish --task <TICKET> --dispatch-id <critic> --needs-author
<cases> --reason "<words>"` (`rework` is refused while it runs; never a message to a closed author), then `recover` prints the critic's retry packet.

With a judge configured, `start` for the window critic (not the plan critic: no code yet) runs
`judge_code.py --task-root <TASK_ROOT> --dispatch <id>` first and hands `work/judge-code-<id>.json`
over: in `mode: on` the critic reviews the flagged tests in full and checks only the unscored
dimensions on a clean one. The
automator is told to run `judge_run.py --remedy` before it writes a `blocked_by_env` row, and
`judge_code.py --cause --finding "<text>"` maps a critic's finding to the `repair_cause` of a
rework instead of your guess. None of it changes what `s5_precheck.py` refuses.

Before dispatching S5, let the controller recheck the current plan against the Gate-A
`plan_content_hash` and oracle hashes produced by `--operation gate-inputs`. A mismatch
returns the affected design to Gate A; do not bypass it or recompute hashes in an agent.

changed `source_revision`, a reason and a nonempty `affected_scope` (active work is
checkpointed first). A code-only change with unchanged requirements, oracle, plan and scope
carries the approval forward by adding `gate_a_applicability` — the prior `decision_id`,
`requirements_unchanged: true`, the unchanged `plan_revision`, the exact `scope` and hashed

stales Gate A, returns S4 to pending and is the only route to a new `qa-case-critic`
dispatch. `references/controller-api.md`, items 5-6.

Before any write, verify repositories, immutable source SHA, ownership and target branch.
Preserve a suitable current branch. Create one only when needed and authorized by project
policy; never create one merely because S5 started.

Take the S5 scope from the controller, never type it: `--operation stage-scope` (and
`stage_scope` in the prepare packet) lists the approved `automate` cases. A dispatch with an
empty scope is refused while the plan names cases for this stage.

Dispatch one window at a time with exactly the `scope` of a `stage_scope.windows[]` entry
(`accepted_by` shows what is done); never merge two. Per window: `qa-automator` writes the
tests of its plan slice (one run per code version of each test, then only the instances whose
code changed; its form answers every remark of the slice with a `plan_remarks` row and every
place where the code is not the plan with a `deviations` row), then `qa-code-critic` with that
receipt — judging the CODE and its fit to the plan, never coverage again; static
review over the files its brief names first, then one `probe_by_code.py` call per new/changed
instance, which walks every check of its test (its `probe` record goes into the window verbatim;
`red_sandbox.py --probe` proves only the one check it names, on the critic's doubt that the check
looks at the product); no repeated green.
**The run budget of a story:** one author run per test and one critic probe per check, a rerun after a
critic's remark only of the fixed tests and only when their code changed (a comment-,
docstring- or marker-only fix keeps its run). A result stands at every later stage while the
tests, the environment and the deployed version are unchanged: a repeat is answered `reused`
(green) or `already_run` (red), a probe repeat `already_probed`, and only a person's word
passes one. Window roles run tests with
`run_suite.py --mine <CASE>`; `--request` is for a run that is not the ordinary one. Merge
windows without overwriting. Record S5, then read `phases/s6.md`.

**A test I cannot run at all.** `stage-scope` marks the cases of a profile the person took
over `handed: true`. The automator still writes them and the critic still reviews them
statically — no run, no red probe. The manifest carries one row per case: `{"case": "<case id>",
"reason": "handed_to_person", "detail": "<profile id>: <the command and the test file the
person runs>"}` (the automator writes it as `@pytest.mark.qa_unresolved(case=,
reason="handed_to_person", detail=)` on the test), and the window instance carries `outcome: "handed_to_person"` with no
`execution_fingerprint` and no `probe`. Complete the window with `unresolved` and a `reason`
naming `handed_to_person` — the controller refuses a handed window that does not say so.
Nothing waits for a result; `import_test_receipt.py` stays an optional door. If `run_suite.py`
answers `{"status": "executor_unavailable", ...}` (exit 3, nothing launched): stop, quote its
`question` verbatim, record the answer the way s4.md does; never hand cases over without that
word. A scope id may read `<area>/<case id>`: roles copy it into `case`/`covers` exactly as
given, never stripping the area.

**A Then the person takes.** When one Then of a case (or a named part of it) cannot be checked
here and the person agrees to check it by hand or on another stand, the automator keeps the
case's green test for the other Thens and writes that Then as `qa_unresolved(case=, then=[n],
reason="handed_to_person", owner=, part=, detail=<the steps>)`: a remainder, never both bound
and left. The precheck then waits for the person's word for exactly that Then, and the automator
returns the item in its digest. Write their words to `state/words/<name>.txt` and record
`waiver.py --task <T> --stage S5 --block "then handed: <case>#<n>" --words-file <file>` (a word
already given for this Then is re-recorded, not asked again). Re-dispatch the automator with
`rework --reason` carrying the owner. Never record `partial-green`: that family is refused at
source and no word passes it. A case whose every Then is left is the whole-case hand-off above.

**A probe that cannot run here.** When the critic's `probe_by_code.py` run is `not_executed` or
`incomplete` for a test that ran green (the tool or the stand stopped it, not the test), the critic
records the verdict `unverified` with `sensitivity_proof_missing_reason` and returns the item in its
digest: a role records no word. `window_record.py` then refuses the item with "probe is missing"
and names this door. Read the critic's probe record first (`verdict`, `cause`, `refused`, `language`) and the probe-run log it names. `cause: judgment` (the run failed at the mutated line on a text the tool cannot read) is the code critic's to judge (`probe_by_code.py --judge`), not a question and not `tooling`; after its `cannot_judge` the person is asked that one question, never covered by a probe-gap word: their own word is `probe not proved: <case key>` (`waiver.py --task <T> --stage S5 --block "probe not proved: <case key>" --words-file <file>`, one word per case, read only when it is not older than the critic's judgment; the report then lists the test as not proved). A record still without the critic's judgment is named by no word at all. Ask the person whether the test may stay unprobed here (or re-record words they
already gave, without asking again) only for `refused: tool`, `cause: tooling`, or a failure site the record does not show (person-owned: gate_word). A word about ONE case (`probe gap: <case key>`; an instance id that is one token works too, a phrase with spaces is never a word the window reads) holds for the tests of that case; a word about a CLASS (below) holds for every test of the class. Say which one the question asks. A probe nobody tried, or one a down stand stopped (including an empty report), still needs its own word. Write their words to `state/words/<name>.txt` and record
`waiver.py --task <T> --stage S5 --block "probe gap: <case key>" --words-file <file>`;
the block names the case key exactly. Then build the record again: it carries a
`probe_gap` block, `window_record.py` exits 0 with "acceptable as unresolved", `story_step.py finish`
derives the pair, and S8 lists the test under "Left with you". Never `*` and never `not receipted`
for this: they pass nothing here. A red test, and a test whose probe ran and judged it, take no word.
When the tool cannot read this language, the critic's record says so (`cause: tooling`, with its `language`): ask ONE question for that language and record `--block "probe gap: tooling:<language>"` with one word; it holds for every test of this story written in that language whose record says the same, and another language is a new question. A word about one test whose probe the tool could not read (`refused: tool`, `incomplete` (other than `cause: judgment`), or `not_executed` with `cause: tooling`) also holds for every other such test of the story, in any language. A word `tooling:<language>` never covers a record with no `cause: tooling` (a stand that did not run). A record that judged the test, a record of other bytes and a red test take no such word.

**After gate A the approved case is the oracle.** A test written to an approved case that
fails against the implementation is this stage's product, not a blocker: it is handed over
RED with `unresolved[] reason: contradicts_requirement` (requirement id, expected, observed),
and S7 decides what it is. The automator and the critic have no "the case is
wrong" route — only that one or `impossible` — so a `deferred_by_decision:*` row arguing with a
case's Then goes back to the role, never to the person, and an existing test written to the
code is never the arbiter. The doubt travels with the red test to S7, where the analyst puts it
to its control experiment and decides: a product bug (`APP_BUG`), a wrong case (`CASE_DEFECT`: it
returns to the designer through `rework`; not a bug) or another outcome the analyst's charter names.
A red test whose manifest row says `contradicts_requirement` for its instance closes its window by
code: `window_record.py` writes `probe not applicable: red` in place of a probe, the critic's
`approved` stands, the record is "acceptable as unresolved", `story_step.py finish` derives the
pair, and no word of a person is asked. `s5_precheck.py` refuses both shapes; no word passes them:
they are the author's repair. Tests left red on purpose are counted, never "unresolved":
`stage_status.py` reads them from the manifest — "N tests red on purpose — the implementation
differs from the approved cases; S7 decides what each one is."

On `run_the_window_first` (exit 2, nothing launched): the role asked for part of a case while
a test of the same file in its own scope had no evidence at all — it runs the one `--mine`
command the answer prints, the whole window in one pytest call; `--purpose repair_verify` is
only what a repair touched. Staleness is per test function (`instance_code_sha`):
adding a test to the file, a comment, a docstring or the marker does not change it; any other
module-level change (a constant, helper, fixture, import, class) counts for every test of the file.
A live check that went stale in a later window is re-probed by that window's critic:
`probe_debt.py --settle` and `probe_by_code.py` admit it outside the dispatch's scope by code (its
review is not re-checked); a test with no receipt outside the scope stays the orchestrator's, or a
person's word. The critic's probe is one command per
instance (the check is live), `probe_by_code.py --task <TICKET> --dispatch <id> --test "<file>::<func>[<param>]"
--instance <IID> [--at <line>]`: with no `--at` it walks every check of that test, and each check needs an entry in the critic's
model file `work/probe-models/<dispatch id>.json` (a check with none is refused before any byte, naming that file); `--at` selects one row
and needs its entry too, and `--mutation invert` is no way past it; the plan is complete only when every check is proved. A plan of more than
3 rows runs in the background and the critic reads its answer; `plan_unfinished` means the wall cut the walk, and the same call continues it. Each check is mutated in turn (the record's `target` says where the obligation's assertion lies: false is outside the test's body and plan), the test (a pytest node; in another language its case, bound by its report id) runs
through `run_suite.py --request` as a `red_probe`, the bytes are restored
sha256-verified, and `work/probes/<IID>.json` is written with the verdict (`intended_failure`,
`no_failure`, `wrong_location`, `not_executed`, `incomplete`) and a row per check; `intended_failure` writes the live
receipt only when every owed check is proved; `incomplete` and a refusal naming a factory data gap or a killed probe's unresolved copy are a
tooling finding, the author's to settle, never a verdict on the test; `--release-copy <file>` drops that
copy once the author has; the critic mutates nothing by hand and retypes nothing; the product level,
`red_sandbox.py --probe` (catches a broken product), proves only the one check it names, and the critic names it with a `product` entry; the others stay owed; a role's final message is the digest form of `common-rules.md` (header, one
line per instance, path) and the exit gate refuses any other shape.

A `blocked` row names what stops it in the form's `blocked.problem` (a stand block is `blocked_by_env`; a factory command that refused your run is `header.verdict: halt` with the refusal quoted in `blocked`).

**The automator's manifest comes from its markers.** The automator marks the tests it writes
(`@pytest.mark.qa(case=, then=, obligations=)` on a function, or on a `pytest.param(...,
marks=...)` row when each parametrize row is another case; `@pytest.mark.qa_unresolved(case=,
reason=, detail=)` at module level for a case with no test, on a function with `then=` for a
clause it cannot assert) and runs `manifest_from_tests.py --task <TICKET> --dispatch <id>
--file <test file> [--file <data module>]` once per window: it derives the instance ids,
`covers`, the pinned `case_version_links`, `obligation_refs`, `assertion_ref` and `status`
from the run block, merges `then_bindings` without dropping another window's rows, and calls
`manifest_put.py` once. **Add `--collect -- <the project's pytest command>`**: the ids are read
out of the source, and a project's own plugins rename a parameter id before pytest collects it
(pytest-playwright prepends the browser), so the manifest would carry a spelling nothing joins —
on TP1-15045 that cost 15 of 27 run rows and surfaced at S8, after the review window was
accepted. With the flag every id is resolved through a real collection, a rewrite is printed, and
an id pytest does not collect at all is a refusal naming the nearest real ones. Without it the
output says the ids are unverified, and that sentence belongs in the handoff. `--dry-run` prints
the fragment; `--help` prints how the project registers the markers (`markers =` in its pytest config or a `conftest.py` line — do it once,
in the project). A hand-written fragment (`trace_binding`, `runs`, `run_witness`, `probe`,
`self_fixes`) still goes through `manifest_put.py --fragment`. Its refusals (an obligation
not on the case's plan row, a case outside the window's scope, an unknown keyword) are
repairs to the marker, never questions for the person. `manifest_from_tests.py` also prints the row form: the fields the window record and the run demand of each `tests[]` row (`window_record.REQUIRED_ROW_FIELDS`), which the automator fills before its first handback; `s5_precheck.py` names every one still missing in one finding.

The automator's dispatch ends at `s5_precheck.py` (stages.json runs it): manifest invariants,
the Then clauses each case proves, the reporter row each test has, five test-code smells, and
the coverage obligations of the scope's plan rows that no `obligation_bindings[]` row reaches
(TP2-2553 handed a window whose bindings were spelled `OB-1` while the plan said
`TS-1-O1`, and the gaps surfaced at delivery, two windows late; `manifest_put.py` now refuses

Its findings go back to the AUTHOR as one repair round, without a critic round; its `hint:`
lines are advice about the shape the author chose and never fail the gate. The critic
gets a clean input and is accepted only with its findings file and `review_receipt_ref`.

<critic-dispatch-id> [--review-receipt]` and handed to acceptance as `--window
work/windows/<critic-dispatch-id>.json`. Never assemble that JSON: the script prints every

acceptance of the last window closes S5 — omit `stage_complete` and it completes; a bare

`execution_fingerprint.py`, provide exact instance-to-reporter mappings, and configure the
selected profile's read-only runtime probe. For a stand that runs in docker the factory
writes that probe itself: `runtime_probe.py --task <TICKET> --profile <id> --environment
<env> --container <name> --checkout <path to the app at the MR's head>` compares the sha256
of every production file the story's diff touches inside the container against the checkout
and prints the `runtime_provenance` record `--mine` needs; onboarding records the call in
`execution.runtime_probes.<profile>`, and a story never writes a probe by hand. What the probe
cannot read is the person's to answer at the stage entry: their decision is kept in
`qa-factory/records/stand-identity.json` (never written by a role), and a build they confirmed for
this story is taken by `--mine` like `matched` and reported as their word. Only a
verified `local_source` profile may use the explicit runtime-not-applicable exemption. If a durable job is interrupted, use the
runner recovery command; never launch a replacement from an ambiguous PID.

## A story held for code

When `next` answers `await_implementation` (S5 is done and a side this story delivers does not exist yet), no stage from S6 runs.
Build the interim report by code and record the wait: `interim_packet.py --task-root <TASK_ROOT> --command "<the command that starts
the story again>"` writes `interim-report.md` (data only: sides, tests per case, what ran and what each run recorded, the open
placeholders); then `controller.py --task-root <TASK_ROOT> --operation await --input <json>` with `packet` and `s5_dispatch`; show
the report to the person and stop. You write no gate B, no verdict, no bug for it. When the code arrives, the person starts the
story again with `--mr`, `--branch` or `--commit` (or `--side <name>=real`); that is `arrive`.

A story HELD FOR CODE (`pipeline.awaiting`): `next` answers `await_implementation` (record: `await --input <json>`),
`awaiting_implementation` or `awaiting_stopped`. `arrive --input <json>` clears the hold (nothing held: only records);
`stop_waiting` and `first_look_continue --source-head <H> --register-hash <R>` take `--words-file <file>`; a stopped story
reopens by `rework` of S0..`held_from`-1 with words, or `arrive`.

## The bind round, after the code arrived

When the arrival leaves a placeholder or a pending test (the register's `provisional[]` has an `open` row, or a `pending_implementation` row
names instances), S5 is reworked for it: `controller.py --operation rework --stage S5 --role qa-automator --cases <the cases of the open rows' dependents and of the pending rows>
--purpose bind --cause source_arrived --reason "<the code arrived: source>" --brief` (a driver's cause: it spends none of the cap), then the code critic and the probe as for any window. The automator's brief lists only the
open rows and the pending instances; it settles each open row on a live run, runs the pending instances and retracts the pending rows whose
instances all ran on real sides. The window's own rules stand; nothing of the earlier windows is redone.

## Runtime first; baseline never blocks execution

Follow `references/environment-preparation.md` before any stand mutation. Inspect the
actual running revision, mounts, startup command and build inputs first. If the target
change is already running, test in place. Never switch back to main, rebuild an old version
or create another stand solely for baseline. If a suitable before state is already running,
capture useful current-case evidence there, then perform only the necessary authorized
update. Missing before evidence does not block any current test, including comparative cases.

`controller.py --task-root <TASK_ROOT> --operation deployment-inputs` reports baseline gaps;
its ready flag is not deployment authorization or a runtime health verdict. Execute current
checks and retain after evidence. Missing comparison evidence is awaiting_baseline, never a
fabricated comparison PASS and never an environment blocker for the whole case. Report
independent current assertions separately; retain real failures. Actual before captures still
use evidence_phase=baseline, exact case/version, revision, fixture, approved assertion and
hash-bound artifact receipts. Capture success is not a product verdict.

At S8 show the after results and incomplete comparisons. Ask where to obtain before evidence
(stand/revision), or whether the user will compare themselves. This follow-up does not delay
completion or retro. Production access or another deployment requires explicit authorization.
Reuse valid after evidence if before is later supplied; rerun only invalidated checks.
Recommended regression remains user-owned. See the reference for preparation job commands.
