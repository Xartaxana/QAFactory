# S7 — Triage

`stages.json` ids used: `S7` (`role: qa-failure-analyst`, `requires: ["S6"]`, inputs
`run-report.json`, `automation-manifest.json`, `evidence/`, outputs `triage.json`,
`bug-drafts/`, `required_outputs: ["triage.json"]`).

Every failure gets a verdict with evidence. Only test defects are repaired here;
application bugs are drafted and wait for gate B.

Oracle insufficiency is a scoped owner gap; reopen Gate A only when the oracle changes.

## Entry check

`run-report.json` exists and `execution_status` is `passed` or `failed`. `env_blocked`,
`broken_run` or `timeout` means there is nothing to triage yet — go back to the S6 halt that
produced it. So does `not_executed`, except after an S6 code-only receipt (nothing to
execute, or everything handed to a person): then it is read like any report, and a story
with no failure in it has nothing to triage.

Nothing to triage means `totals.failed == 0` AND no manual check whose `result` is `fail` or
**`inconclusive`**. An inconclusive check is a check that did not answer: it has an owner and
a next step, so it is triaged like a failure and never reaches gate B untouched. A red test
carrying a `contradicts_requirement` row in `automation-manifest.json` is likewise a failure
to triage, not a known one to skip.

With none of those → dispatch no triage, run section Investigation, then
record `S7.status: done` with digest `no failures — nothing to triage`, journal
`--event dispatch_skipped --task <TICKET> --reason "S7: no failures to triage"`, and move on.

## Code answers first (`s7_pretriage.py`)

Before the analyst is dispatched, code writes the one kind of row it can: a manual check that
ended `inconclusive`, whose record validated and carries a limitation of the runner's own
(not the identity sentence code adds), with no `contradicts_requirement` row for its case. The
row says `verdict: NOT_EXECUTED`, `source: code`, quotes the limitation verbatim and says where
it came from. A red test is never pre-judged by code, whatever its manifest row says
(`blocked_by_env` included): it goes to the analyst.

- Every failure answered that way, and no `contradicts_requirement` row anywhere in the manifest
  (even for a case that is not failing: CASE_DEFECT is the analyst's alone) → run section Investigation, then S7 closes by code
  (`code_only`), digest `every failure has a state the run already recorded: <n> written by code`, no analyst.
- Otherwise the dispatch names only the failures left, and one line names the code rows: keep
  them, list them under `not_for_repair` and in the scribe form, replace one only with your
  own row. Code never writes over an analyst row; it restores a code row you dropped.

Places to settle (t-1991): the suspicions the run left unchecked (code-reading drafts, the runner's doubts, register lines) are listed by

expectation whose source is not `none`), `not_a_bug` (with `why` and the words seen), `requirement_silent` (with the question for the person,
never a bug) or `impossible` (with `why`); the expectation names its source: `requirement`, `question`, `person` or `none`. A place the dispatch
ended without settling is a gap, not a pass: at every point this phase closes S7 by code, run
`place_answers.py close-unsettled --task-root <TASK_ROOT> --why "<one of gap_reasons>"` BEFORE section Investigation (the driver closes in the
same order). `gap_reasons` (`references/place-answers.json`): the dispatch ended without an answer for the place; the stand could not be
reached; the walk session could not be opened; no analyst ran because there was no failure to triage; no analyst ran because every failure had
a state the run recorded. A place whose register chain the analyst withdrew cannot take another line: when it is unsettled again its gap is
written under the target `place-gap-<place id>` (`gap_target_prefix`). The investigation dispatch does not walk or answer these places.

Verdicts come from the closed list: `APP_BUG` · `TEST_BUG` · `TEST_BUG:collection` · `ENV_ISSUE` ·
`FLAKY` · `APP_CHANGED` · `CASE_DEFECT` · `ASSERT_STRICTER` · `RUNNER_MISREAD_EVIDENCE` · `NO_DEFECT`.
You never assign, adjust or argue with one.

A red on an extra or different value gets the control experiment first (the analyst's technique "The control experiment"): the
same action without the change, one command, its output under `evidence/`, recorded as `control` on
the row. Data weaker than the case's Given alone is a `TEST_BUG` of the data, repaired below; the
effect without the change, with the requirement silent on what the assert asks, is `ASSERT_STRICTER`
(both, weak data and the effect: `ASSERT_STRICTER` with `given_gap`); otherwise `APP_BUG`, or
`CASE_DEFECT` (the analyst's "A case that misread the requirement is a defect of the case") when no effect shows without the change. An experiment the stand cannot run
is named, never read as a pass.

## Repair — `TEST_BUG`, `TEST_BUG:collection`, `FLAKY`, and the `reorder` of a red

These three verdicts are repaired, and so is a row that carries `reorder: true` (any verdict; in practice an `APP_BUG` whose
independent Thens stand behind the red one). Nothing else is. A round is registered by the controller before the author runs; a
bare `Agent(qa-automator ...)` is never launched, because the guard knows no such round. For each failing test, at most **two
rounds**, shared with the S5 rounds of the same window (the controller's count; the reorder round is counted in that same S5 cap):

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/controller.py" --operation rework --stage S5 --role qa-automator --cases <case> --cause test_defect --reason "S7 fix: <test> - verdict <TEST_BUG | TEST_BUG:collection | FLAKY>" --brief
python "${CLAUDE_PLUGIN_ROOT}/scripts/story_step.py" materialize --task <TICKET> --dispatch-id <the id the rework prints>
```

Launch the author by the card `materialize` writes (the stage's `rework_mode`: `fresh` is a NEW agent, else `SendMessage`). The
brief tells it the test, the verdict, the mechanism (`FLAKY` only), the paths of `triage.json` and `automation-manifest.json`, the
round "<r> of 2", and that retry annotations and sleeps are forbidden and the Then-lines before and after the fix must match.

A repair of a test the critic had rejected ends in a critic review of that one test. When the manifest holds `critic_verdict:
rejected` on a test of the case, the fixed test is NOT repaired on the author's green run: register the review the same way
(`controller.py --operation rework --stage S5 --role qa-code-critic --cases <case> --cause test_defect --reason "S7 repair review:
<test>" --brief`, then `story_step.py materialize`). The test is repaired only when the critic does not send it back; a blocking
`test_defect` finding is one more round within the cap, a halting verdict, `unverified` or `rejected` stops the test (the row
stays red in the triage and travels to the report). A repair of a test the critic had not rejected has no review.

### The `reorder` round

A triage row with `reorder: true` (it names `blocked_thens`) asks the author to MOVE the asserts of the independent Thens above the
red one: the Then lines and the expected values stay as they are, the test stays red at the same Then. Nobody comments out the red
Then. One round is these steps, in this order (`s7_reorder.py start` opens it, `finish` closes it):

1. Snapshot the test file before the round; the command prints the author's reason and registration, and keeps an open snapshot
   across a refused round:
   `python "${CLAUDE_PLUGIN_ROOT}/scripts/s7_reorder.py" start --task <TICKET> --instance <instance id of the row>`
2. Register and launch the author with the `author` command and brief that `start` printed (reason `S7 reorder: <test>`, cause
   `test_defect`), then `story_step.py materialize` as above, and append the brief lines `start` printed to the prompt of the card
   (they carry the order of the Then rows to pin). The author re-runs only this test, `--purpose repair_verify`.
3. Judge the round and carry the triage row to the new attempt. It refuses when the edit is more than a move of lines of the
   test's function, when the new run is green (a reorder never turns a red green), or when no new `repair_verify` run exists:
   `python "${CLAUDE_PLUGIN_ROOT}/scripts/s7_reorder.py" finish --task <TICKET> --instance <instance id of the row>`
4. Register and launch the code critic with the `critic` command and brief that `finish` printed (reason `S7 reorder review:
   <test>`), appending the brief lines `finish` printed to the prompt of the card: it reviews that one test (rubric dimension 6 and
   "the asserts only moved, no Then text changed"). A reorder is repaired only when the critic does not send it back; a blocking
   `test_defect` finding is one more round within the cap, a halting verdict or `unverified` stops the test (the row stays red in the
   triage and travels to the report). When the critic approves, mark the carried row (it writes `fix_result: fixed` on a row `finish`
   carried, and refuses any other; a round already carried is resumed at this step, never at step 2):
   `python "${CLAUDE_PLUGIN_ROOT}/scripts/s7_reorder.py" mark-fixed --task <TICKET> --instance <instance id of the row>`

The reorder round shares the S5 window's repair cap (cause `test_defect`); a round past the cap is the `s7.repair_limit` question
to the person (person-owned: gate_word), not a new counter. When the controller refuses the registration with the plan order (`plan before windows`), the
reorder round is not repeated silently: the person is offered their word, with its price. The word waves the plan order through for
this story's S5 windows (the pass is recorded in `state/passed-by-person.jsonl`), it costs the person one answer per such round, and
it does not rewind S5 or S6 (their statuses do not change). With their words in a file:
`python "${CLAUDE_PLUGIN_ROOT}/scripts/waiver.py" --task <TICKET> --stage S5 --block "plan before windows" --words-file <file>`

What the person hears about a repair round is one line, built by code, never your retelling:
`stage_status.py --task <TICKET> --event author_repair --fact stage=S7` (and `role_halt` with
`--fact stage=S7` when a round stops). The verdicts and the analyst's reasoning stay in
`triage.json`; the path is offered only if the person asks.

After each round, re-run **only the failed test**, never the suite. Build a fresh typed
`purpose: repair_verify` RunRequest whose selected/current-scope instance list contains
only the failed instance, then run:

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/run_suite.py" --request <request.json>
```

The request's framework-specific `selector_args` supplies the exact node selector. An
unsupported selector remains unresolved and must not fall back to a file or suite run.

Need the detail of one failure? `run_suite.py --task <TICKET> --label <label> --detail
<test>` reads the already-captured log. It does not re-run anything, and neither do you.

**`FLAKY` needs confirmation, not a passing re-run.** A `FLAKY` verdict is valid only with
**3 isolated executions of that one test** on the same head, recorded as evidence, and
a mechanism from the closed list (`isolation · race · timing · shared_state · teardown ·
environment · unknown`). The executions the automator and the critic already ran count, and
so do S6's failure and the inner runs of a `--reruns N` launch; the analyst runs the rest as
`flaky_diagnostic` reruns — S7 only, up to 3 per test and code bytes; the code refuses a
4th and earlier executions never raise that limit. After the fix the new bytes get a series
of their own, up to 3 `flaky_diagnostic` reruns: one green does not confirm a flake fix.
Fewer than 3 executions, or a missing mechanism, is a rejected verdict — back to the
analyst, not a number you fill in.

Not fixed within the cap → the test is **not verified**: `fix_result: not_fixed` puts it
into the ledger as `not_verified_flaky` and `delivery_ready` turns to no. Quarantine is not
yours to grant — it exists only as a gate B decision with a debt file and a trigger.

## No repair — `APP_BUG`, `ENV_ISSUE`, `APP_CHANGED`, `CASE_DEFECT`, `ASSERT_STRICTER`, `RUNNER_MISREAD_EVIDENCE`

- `APP_BUG` → the analyst writes a draft under `bug-drafts/`. **No bug file is created
  here.** `bugs/BUG-n.md` exists only after a gate B decision names that draft. A test the
  automator handed over red with `unresolved: contradicts_requirement` goes through the control
  experiment first (the verdicts are above); an `APP_BUG` draft quotes the requirement id
  and the expected and observed value from that row. The expectation is never adjusted to the code.
  The one thing an `APP_BUG` row can hand to the automator is a `reorder` (section Repair): the row then carries `reorder: true`
  with `blocked_thens`, the author only MOVES asserts, and the test stays red; the draft and the row stay as they are.
  **Every draft carries `triage_ref` (the `triage.json` row it rests on), `manual_steps` a
  person can follow in the product, and `confirmation: unconfirmed`** (plus `reproduction` when the analyst saw the
  red again: the code derives `reproduced_by_factory` from it). A red result with no
  verdict never becomes a bug: the gate B rehearsal names it as the factory's own to repair,
  and on TP1-15045 two of four bugs shown to the owner had no triage row at all.
  **One draft per mechanism.** Before drafting, the analyst lays the `APP_BUG` rows and observations side by side
  (`python "${CLAUDE_PLUGIN_ROOT}/scripts/bug_neighbours.py" --task-root <TASK_ROOT>` prints what they share, a hint and never a verdict). Failures
  that show ONE cause are ONE draft: `mechanism` (the statement, how far the analyst got, the basis it stands on) and `manifestations`
  (every way it shows, each with its own evidence and red test). Merge only on a `confirmed` cause whose basis the code can re-read; a
  suspicion keeps separate drafts that name each other (`possibly_same_cause`). Every new triage draft carries `mechanism` (status `unknown`
  with the reason is the empty outcome); the key page of the draft is `references/slices/qa-failure-analyst/artifact-contract-run.md`.
- `ENV_ISSUE` → `owner: factory` is fixed in this stage by the analyst and re-run;
  `owner: user` becomes a gate B item with the concrete list. Every `ENV_ISSUE` row carries
  the dismissal formula (`our_signal` / `env_fix` / `unverified`).
- `APP_CHANGED` → recorded with the commit or MR quote proving intent. Never on a row whose
  oracle is `history:` — that combination stays `APP_BUG`.
- `CASE_DEFECT` → the approved case misread the requirement, proved by the requirement text in
  the register (an existing test is never an oracle). No bug and no draft: `controller.py
  --operation rework` returns that case to the designer with the analyst's evidence. Only a
  test handed over red with `contradicts_requirement` can reach this verdict, and only after the
  control experiment showed no effect without the change; when the register backs the case as
  written, it stays `APP_BUG`. A row with `field_absent` is judged by its `shape_ref` instead
  (`agents/qa-failure-analyst.md` 2b): the case's own requirement and the data held nowhere is
  `APP_BUG`; without a `shape_ref` the rule does not apply. With the effect there and the requirement silent, it is never
  `CASE_DEFECT`, even when the assert is the case's own Then.
- `ASSERT_STRICTER` → no repair, no draft, no rework, no gate A: the assert asks more than the
  requirement, proved by the control experiment (`control` on the row, its file under `evidence/`).
  Code builds the Left with you line from the ledger; the person removes the assert or refines the
  requirement. Nobody here rewrites the test or the case.
- `RUNNER_MISREAD_EVIDENCE` → a manual runner's `fail` that the text its own attempt captured contradicts (the row carries
  `contradiction`). No bug, no draft, no repair: S7 stays open until the runner judges the SAME captures again (nothing is captured
  again): `controller.py --operation rework --stage S6 --role qa-runner --cases <case> --cause reviewer_error --reason "S7 re-judge:
  <case>" --brief`, launch the runner by the card, then `finalize_task.py`. At most `repair_cycles` rounds per case and attempt;
  past that the red stands, owner `factory`, and delivery says `no`. The delivery stays red until a new record replaces the result.

## A Then behind a red

When the person asks to check the Thens a red stopped, read first: the case's triage row (`blocked_thens`, `blocking_check`,
`diagnostic`) and the case file's Self-probe notes. A Then the row lists behind a defect cannot answer until that defect is
fixed: say so in one sentence with the bug, and start nothing. A Then with a `diagnostic` outcome already: quote it. Neither
recorded -> the analyst's one diagnostic run: `controller.py --operation rework --stage S7 --role qa-failure-analyst --cases <case>
--cause question_answer --words-file <file> --brief`, never `rework --stage S5`. Before it runs, tell the person its price (person-owned: money): when S8 or
gate B is already done, their words make the report writer run again, and gate B is asked again. Moving the asserts for good is
the S7 repair `reorder` (section Repair). A rework carrying the person's words always takes `--words-file`, never `--reason`.

## Investigation — before every close by code

At every point this phase closes S7 by code — "nothing to triage" (section Entry check), "every failure has a state the run already
recorded" (section Code answers first) and after the repairs (section Exit) — first run
`investigation.py project --task-root <TASK_ROOT> --dispatch S7`, then `investigation.py unresolved --task-root <TASK_ROOT>`, and read
its JSON:

0. A member of `pass_members` with status `running` → no close and no `close-gaps`: resume that dispatch (`story_step.py` binding) and
   come back here when it has ended (the same rule as the driver: a running pass is waited for).
1. `budget_problems` not empty → no dispatch: `investigation.py close-gaps --task-root <TASK_ROOT> --why "the investigation is not
   available"` (a budget nobody can read resolves nothing and would refuse every probe).
2. `unresolved` not empty, `pass_members` empty and `gate_b_answered` `false` (`null` — an unreadable `pipeline.json` — counts as not answered, as in the driver) → `story_step.py start --task <TICKET> --stage S7 --role
   qa-failure-analyst --purpose investigation`, bind, finish with `--not-complete`; then `investigation.py close-gaps --task-root
   <TASK_ROOT> --why "the investigation ended before this target"`.
3. A pass already made and ended (a member of `pass_members` that is not running) → `close-gaps` with "the investigation ended before
   this target" (one pass per S7 chain).
4. `gate_b_answered` `true` → `close-gaps` with "gate B is already decided".

`close-gaps` records as a gap only a target that is still in `unresolved`; one the triage already resolved is left as it is. `unresolved` empty → close as below, nothing to add. The investigation is read-only: the analyst reaches the stand only through
`investigation_probe.py http` (GET/HEAD/OPTIONS, within the caps of `references/investigation-budget.json`), and `http` itself refuses
a second investigation in one S7 chain. Then close as the section that sent you here says, adding `work/exploratory-findings.jsonl` to
the evidence when it exists.

## Exit

1. `Grep` `triage.json` for the verdict counts only — one line. Do not read the file.
2. After section Investigation, record the stage: `stage_done.py --task <TICKET> --stage S7 --status done --role
   qa-failure-analyst --digest "failures=4 app_bug=2 test_bug=1 fixed=1 flaky=1
   not_fixed=0"`. Nothing to triage means no role ran it: drop `--role`. The fix rounds add
   their own events through `log_append.py --batch` — `accepted` per round with the run
   witness, `rejected` with `--failure-class` and `--reason-family` for a round that failed.
3. Print the S8 card: `story_step.py card --stage S8`.

## Halts of this phase

| Digest | Action |
|---|---|
| `cannot triage — <what env_probe/run_suite reported>` | Verbatim, stop. The environment is unusable, not the triage. |
| `repair cap reached, unresolved: <tests>` | The list of tests still failing. No third round; they travel to the ledger. |
| A `FLAKY` verdict with fewer than 3 re-runs or no mechanism | Rejected by the validator; one re-dispatch of the analyst, then halt. |
| `triage.json` missing after `done` | Not done. One re-dispatch, then halt. |
