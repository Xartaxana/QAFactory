# S3 — Plan

Use `references/coverage-design.md`. Each v2 plan row keeps its stable ID and adds
`schema_version: 2` and `coverage_obligations[]`. Assess relevant candidate assertions,
prefer reuse/extend before new, retain partial-search gaps, and order ready current-task
obligations by dependencies and risk. Define exact manual evidence policies during design.
S3 does not run tests, regression, or new agent calls.

## The two windows and the plan

After the author's stop (window 2, or the single window) the driver dispatches `qa-case-critic` for this stage; its verdict is recorded with `stage_done.py --acceptance` before its finish; repair rounds follow `repair_budget`. Window 1 (labelling) is never judged by the critic.

**S3 runs in two windows when the story has an implementation diff** (`implementation_source: diff`),
in this order (the driver runs the same steps, `Driver.stage_S3`): prepare, window 1 (labelling),
project the claims, accept window 1 open, check the table, window 2 (the plan), project again.

*Prepare* (diff world):

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/blast_radius.py" --task <TICKET>
python "${CLAUDE_PLUGIN_ROOT}/scripts/grounding_table.py" --refresh --task <TICKET>
python "${CLAUDE_PLUGIN_ROOT}/scripts/base_slice.py" --task <TICKET>
```

A non-zero exit of the first or the second stops here (the table is not built over a missing or stale index).
A non-zero exit of `base_slice.py` is a warning, not a stop:
`stage_done.py --task <TICKET> --warn "base_slice: unknown - S3 preparation: base_slice.py exited <n>: no base slice for this story; the planner reads before: unknown"`.

*Window 1 — labelling.* The role writes NO plan: it fills `work/grounding.yaml` (rows, requirements, risks
`K-n`, code areas `B-n`, claims). Name `work/grounding.yaml` and the fields in the dispatch text; the brief carries the labels and the requirement states
(code builds that line from the vocabulary), so never send the role to `handoffs/vocabulary.yaml`: the pre-tool guard refuses
a role the plugin's files, and a dispatch that only named it ended in that refusal (OH3-14). The
fields it fills: `rows[].label`, `.requirements`, `.risks[{id: K-n, hypothesis}]`, `.question`, `.reason`, `.hunks`
(the `all:<repo>:<file>` grouping); `requirements[].state`, `.hunks`, `.where`, `.question`;
`blast_radius.areas[].matters`, `.why`, `.text_says`, `.regression`, `.add_tests`; `claims[]`. A `question` is prose
of at most 300 characters; `before` / `now` values are in double quotes. Tell the role, verbatim:

> **A behaviour the register does not hold.** When a `behaviour_change` row of `work/grounding.yaml` shows behaviour no requirement of
> `work/requirements-register.md` states, write it as one entry of `claims` in `work/grounding.yaml` (never in the register: its writer is the
> requirements tester, and the code copies your claim into it after this window). Fields: `r` (the next free `R-<n>` — the register's ids
> and every other claim are taken), `row` (that row's id), `requirement` (one verifiable statement), `impact` (the project's scale), `before`
> and `before_ref` (what the code did before the change and where you read it — `diff:-<path>:<line>`, `base:<rev>:<path>:<line>` from the
> base slice, `absent` for a new path, or `before: "unknown"` when nothing shows it — never a guess), `now` and `now_ref` (`diff:<path>:<line>`),
> `differs` (yes / no / unknown), `question: raise`, and `ask` (`question`, `source_says`, `severity`, `owner_role`: what the person is asked).
> Put every text value in double quotes. A claim is a statement about the code for the person to confirm, never the expected value of a test.


When `claim_projector.py` printed a projected row, run `grounding_table.py --refresh --task <TICKET>` before `finish`
(the register moved). A problem it names as the role's goes back to the role. Window 1 never closes S3.

*Between the windows* (`grounding_table.py --check --task <TICKET>`): a finding R0, R1, R2 or R5 is read by who acts, which the
line says. R5, or an R0 the driver's preparation cures, runs the prepare commands again and sends back to window 1; an R0, R1 or
R2 the role cures sends back to window 1. Any other R0, R1 or R2 (the line names the driver or the conductor: the diff has no
hunk, no hunk bodies, the register cannot be read, a table the conductor must rewrite) is not the role's, and window 1 would only
repeat it: stop and give the line to the conductor (P22), neither window runs over it. A person's word passes a finding
(`waiver.py --task <TICKET> --stage S3 --block "<part of the line>"`). Findings R3, R4, R8 are the exit's. Nothing is asked of
the person between the windows in this release.

*Window 2 — the plan* (three commands, `references/judge.md`; with a judge configured `start` runs `judge_plan.py`

A risk `K-n` that no plan row tests (a row on `skip`, `manual-human` or `unverifiable`, or none) is not lost at delivery: the check at S8 lists it
as a bug candidate in "Left with you", and gate B can send it to the failure analyst as a bug report. A row for a `K-n` takes its Then from the
requirement the risk serves; when none states the value the row says `oracle_unknown: true` and asks the question (no value from the code).

Off the diff (`implementation_source` other than `diff`): one window as before — `grounding_table.py --refresh --task <TICKET>`
first (it writes the null outcome), then the window-2 commands without the labelling window.

**The plan is written in parts.** On 21.09 the strategist lost two whole dispatches to the
host's output-token cap, twice, writing a 111 KB `work/test-plan.json` in a single `Write`.
Say so in the dispatch: write the file as `{"rows": [ ... ]}` with the first few rows, then
**append the remaining rows with `Edit`**, a few at a time, each edit replacing the closing
`]}` with the next rows plus `]}`. `planning_contract.py` reads the finished file and does
not care how many calls wrote it; `artifact_packet.py --operation patch` is for a later
bounded change, not for building the file (its whole request is capped at 8 KiB). The same
holds for `test-plan.md`.

**The register reaches the plan** (the exit refuses a register id with no row; the dispatch text carries this sentence). Every id of the `## Register` table reaches a row: name it in `requirements` in work/test-plan.json and in the `R` column of test-plan.md. A requirement waiting for a gate A question: `disposition: unverifiable`, `question_refs`, and `if_answered` with a patch that sets a disposition; one that should not be checked: `disposition: skip` with the reason. `not_planned` holds only `K-n` and `B-n`.

**Both big files are read by section.** `work/grounding.yaml` and `work/test-plan.json` are read by section: a whole
`Read` of either is answered with the map of its sections (id: lines); read the one you need with `offset`/`limit`, and
read everything you need before your first `Edit` of the turn (the lines below an `Edit` move). Change a row or a
requirement line in one `Edit` — every field of it at once — and send the `Edit`s of several sections in one turn; in a
code area `B-n` change only the fields that are yours. Say so in the dispatch text of both windows.

Dispatch `qa-test-strategist` after S2. It writes `test-plan.md` from the requirements
register, grounding bundle and project strategy. Each row states behavior, risk, oracle,
existing coverage, chosen level, variants, environment, disposition, reuse choice and the
user regression recommendation. A `|` inside a table cell of `test-plan.md` is written `\|`; a bare one is refused.

A question marked `severity: blocker` (or marked nothing) that is still open stops the stage
after the strategist's handoff: the person answers it first, or passes it with `go on`. A
question the person keeps open until the report is not asked again; the plan keeps its
unanswered branch.

Validate and record S3, then continue directly to S4. There is no Gate A here: cases must
exist and receive independent design review before the human approves scope. A material
unknown becomes a checkpointed blocker rather than an invented row. Print the S4 card: `story_step.py card --stage S4`.

**Remarks after S3 closes.** S3 remarks appear only for a branch finding the S3 exit does not refuse; the S4 rehearsal is the backstop for the rest. `finish` may print an `S3 remarks:` line: S3 is accepted, and question-branch findings remain. They come ALL at once, in one package file the line names. Run the one rework command it prints, `materialize`, and launch the card as S3's `rework_mode` says (`fresh`: a NEW agent, `bind` its id). A remark standing after that round is the S4 rehearsal's, or a person's word (`waiver.py --task <TICKET> --stage S3 --block "<part of the line>"`).

Do not re-run the plan contract by hand: the strategist's exit gate is the check; nothing is run for it. The write hook already ran it: `work/test-plan.json`
is validated by `planning_contract.validate_plan` the moment the strategist saves it, in both
shapes it writes (`{"rows": [...]}` or a bare array), and only the invalid rows go back to
their author, inside that same turn. The structured plan and human test-plan.md must cover
the same IDs, risk/depth and scope.

Two fields decide who reviews a row: the plan's `impact` is the risk scale of
`risk-policy.md`, while the register's damage class travels as `impact_class` — and a row the
register's `## Contradiction matrix` touches carries `source_conflict: true` or
`oracle_unknown: true`, which forces independent design review at S4 and puts BOTH readings of
the contradiction in front of the owner at Gate A (`gate_brief.py` builds them from the matrix
row: the requirement as the register wrote it, and what the source it contradicts says, each
with what follows once it is chosen). The strategist walks the matrix; the exit gate checks
that every `contradicts` cell reached a row. The contested assertion of such a row is not
automated until the owner answers — the rest of the row still may be.

The S3 exit gate re-runs the same script with no arguments and applies exactly what
`controller.py --operation gate-inputs` will require at Gate A, in both plan-contract modes —
so a plan row problem is repaired by its author here, not discovered after S4 and two critic
rounds. The revision mark `coverage_contract_revision` is written by code when S3 closes (a row
carrying another revision is refused); a question a row names as `new:<n>` is raised then too.
It also prints `WARN` lines for `automate` rows at level
`e2e-ui` that carry no highest-risk reason; a warning is a question for the plan, never a
refusal. A person's word passes any of its lines
(`waiver.py --task <TICKET> --stage S3 --block "<part of the line>"`).
